# FolderLock v1.0.5 — In-Folder Lock/Unlock Design Gate

Status: **research + isolated Windows Shell Link proof-of-concept only**.
The v1.0.4 source, main branch, AES/Instant internals, and published releases must remain unchanged until Windows validation passes.

## Problem

Users want one-click-accessible Lock and Unlock icons **inside each protected folder**, avoiding manual navigation into the application. v1.0.1 stopped dropping duplicate helper EXEs because executable replication and self-deletion heuristics contributed to security-product warnings. That history does **not** prove a unique malware detection root cause for every antivirus engine.

## Alternatives and decision

| Option | Strengths | Problems | Decision |
|---|---|---|---|
| Copy `Lock.exe`/`Unlock.exe` into every folder | Literal original UX | Duplicates unsigned PE files; update/removal and AV behavior; self-deletion history | Rejected |
| Windows `.lnk` to one central FolderLock.exe | Two familiar double-clickable icons, no duplicated EXE; standard Shell COM | Central app must remain at the expected path; shortcuts can be modified; needs ownership-safe storage | **Preferred, pending Windows tests** |
| Explorer right-click only | No extra folder files | Does not satisfy in-folder icons | Secondary option |
| PowerShell/VBS launchers | Easy to generate | Script host/process-chain and malicious-shortcut abuse concerns | Rejected |

The `.lnk` files will use Windows Shell Link APIs, transparent target/arguments, and **no passwords, keys, commands, hidden scripts, or network calls**. Do not run a command interpreter, unpack or duplicate EXEs, conceal subprocesses, auto-delete executables, or weaken antivirus policy.

## Required complete UX (not yet implemented)

- Folder must contain both `FolderLock - Lock.lnk` and `FolderLock - Unlock.lnk` before and after either protection mode, with no duplicates across repeated lock/unlock.
- Double-click Unlock -> existing minimal password-only prompt -> detected mode (AES or Instant) -> safe restore. Never leak or save plaintext passwords in shortcuts.
- Double-click Lock -> new minimal lock dialog, not the full app. For first lock, confirm mode (AES or NTFS) and password. For subsequent lock, use explicit user confirmation and existing safe relock flow; never silently bypass password rules.
- If executable has moved, show actionable broken-shortcut/repair guidance. The shortcuts require a local central installation; portable-folder relocation is not transparently supported.
- Opt in or explicitly inform the user during initial folder protection. Provide safe repair/removal controls later, without changing user-owned shortcuts.

## Critical integration requirements and release blockers

1. **AES & Instant root visibility**: currently AES scans and encrypts folder contents, and Instant moves items into `.locked_data`. The links must remain visible while locked. Do not simply add their filenames to unverified reserved metadata lists: that would repeat previous plaintext-exclusion vulnerabilities.
2. **Ownership**: application-maintained shortcuts must be identified by exact pathname + verified target, arguments and/or registered content hash, not just filename, tag, or editable marker. Pre-existing files of the same names must be preserved or fail closed.
3. **No loss on conflict or interruption**: repair cannot overwrite, replace, delete, or silently relocate user files. Killed-process and transaction journal test cases must cover launcher creation and later recovery.
4. **Concurrency**: a shortcut edited between validation, scanning and cleanup must not be silently excluded from encryption. Use strict preflight and transaction-safe handling; do not treat a mutable filename as authority.
5. **State changes**: GUI, CLI, quick-relock, recovery and old vaults must converge to one launcher lifecycle; no duplicates in a 10x AES/Instant cycle, including reparse points, case-insensitive collisions, Unicode and long paths.
6. **Execution boundaries**: shortcuts must target only the known central FolderLock.exe with explicit, safely quoted folder arguments. User-modified shortcut must be treated as user data, not trusted app content. No executable/script copy in target folders.
7. **Compatibility**: FLCK02/FLCK03 vault structures and password checks must not change. Existing v1.0.4 folders without shortcuts remain usable.
8. **Rollout**: never update `main`, version number or create v1.0.5 release until full Windows COM behavior, CLI modal launch, ownership, and security tests pass.

## Validation phases

**Gate A — Shell Link prototype** (this branch): compile and create real `.lnk` files only in TemporaryDirectory on Windows 11; inspect target/args/working dir with native Shell COM. Confirm user-name collision no-overwrite, standard Explorer double-click, no WScript/PowerShell, and antivirus logs. No real folders touched.

**Gate B — Integration**: implementation of state-specific minimal dialogs, central EXE location, ownership registry and verified AES/Instant exclusions; add explicit tests for corrupt/forged shortcuts, crashes, concurrency, paths with spaces, moved installations, and failure rollback.

**Gate C — Windows full test**: all previously passing 77 tests PLUS feature-specific suite, FLCK02/03, packed Onefile+Onedir end-to-end, 10 repeated cycles with pre-existing user-owned `*.lnk`, wrong password and aborted operations. Verify hashes of every original user file.

**Gate D — Antivirus and release**: with real-time protection enabled, independently test on Windows 11 with Microsoft Defender and Kaspersky Premium; record exact detection category, process tree, quarantined path, timestamp and hashes, and check SmartScreen and Smart App Control separately. Submit confirmed false positives rather than disabling protection. For publishing, sign binaries with validated publisher identity when possible and reproduce builds. Publishing is a distinct user-approved step.
